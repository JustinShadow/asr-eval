## 1. 目标、边界与非目标

### 1.1 要回答的三个问题

1. **同一个模型**在不同量化 / 编译 / 硬件上部署，准确率与性能差多少？
2. **同一台设备**换版本（固件 / 服务 / 模型）后，有没有退化？
3. **同一批结果**换一套评分口径，结论会不会变？

### 1.2 边界

- 内部测试/项目组共用，单台服务器，局域网
- 被测对象是自研硬件（205 / 600 / 502），模型服务统一 `etsllm`，接口同源
- 数据集以开源为主（AISHELL / KeSpeech / AliMeeting / MagicData / APY），客家话自建
- 3~5 人，首版 8 周

### 1.3 明确不做（一期）

| 不做 | 原因 |
|---|---|
| 人工标注/校对工作流 | 外部工具产出标准稿即可 |
| 多租户与项目隔离 | 单部署，角色足够 |
| 模型自动部署到设备 | 风险高，`prepare` 只作运维动作 |
| badcase 自动聚类 | 先做筛选 + 人工打标 |
| 旧平台数据迁移 | 已确认：旧平台并行只读 |

## 3. 总体架构

```
接入   React SPA · OpenAPI · CI · LDAP
应用   FastAPI（dataset / benchmark / run / report / device / speaker）
执行   Scheduler ─► SlotPool ─► Adapter SPI ─► 设备
                  └► Scorer ─► Metric Plugin ─► Aggregator
数据   PostgreSQL（含队列/租约）· 本地对象目录 + 只读 NFS
```

### 3.1 四个"分离"

| 分离 | 收益 |
|---|---|
| 数据与计算 | 音频只引用不搬，指标可重算 |
| 定义与执行 | Benchmark 可复用，Run 可重跑 |
| 推理与评分 | 改口径零设备成本 |
| 编排与适配 | 三类设备一个 SPI |

## 4. 领域模型

### 4.1 六个实体

| 实体 | 定义 | 不变性 |
|---|---|---|
| `DatasetVersion` | 冻结的考卷：音频 + 参考 + 时间轴 + 标签 | 不可变 |
| `Deployment` | 冻结的考生：设备 + 固件 + 服务 + 模型 + 量化 + 能力 | 不可变 |
| `Benchmark` | 考卷 + 口径 + 抽样 + 分桶 + 参数 | 不可变 |
| `Run` | 一次评测 = Benchmark × Deployment[]，`kind` 决定节奏 | 结果不可变 |
| `Hypothesis` | 推理产物，内容寻址 | 不可变 |
| `Score` | 打分结果，可重算 | 可重算 |

### 4.2 三个身份

```
content_uid    = sha256(item_key|audio_sha|ref_sha|lang)[:24]
deployment_uid = sha256(platform|bigversion|etsllm|accel|model_key|model_version|slots)[:16]
benchmark_hash = sha256(sorted(content_uid[])|profile_hash|sampling|params)[:16]
```

**不变式**：三者相同 → 结果可比；任一不同 → 必须在 UI 显式提示，禁止静默并排。

### 4.3 两条入口，一张表

- 数据集页：DatasetVersion → 勾多个 Deployment → 横评
- 设备页：Deployment → 勾多个 Benchmark → 回归
- 写入同一 `run` 表，报表只是 pivot 方向不同

## 5. 数据流

```
① 导入   原始目录 → scan → manifest → PG(item/ref_segment) + NFS 引用
② 组卷   DatasetVersion + MetricProfile + Sampling → Benchmark
③ 开跑   Benchmark × Deployment[] → Run（冻结 snapshot）
④ 推理   分片 → Slot → Adapter → Hypothesis（命中缓存则跳过）
⑤ 打分   Hypothesis × Profile → case metrics → 聚合 + CI
⑥ 出报   矩阵 / 分桶 / 回归 / Badcase → HTML / XLSX
```

### 6.4 执行

| 项 | 设计 |
|---|---|

## 7. 横切关注点

### 7.1 可复现性

| 手段 | 保证什么 |
|---|---|
| `content_uid` + `dataset_version.manifest_hash` | 题目可复现 |
| `deployment_uid` + `run.snapshot` | 考生可复现 |
| `profile_hash` + `benchmark_hash` | 口径可复现 |
| `hypothesis.raw_uri` | 原始响应可追溯 |
| `scorer_version` | 打分算法可追溯 |

### 7.2 性能预算

| 场景 | 目标 |
|---|---|
| 10 万 item 列表 | < 300ms |
| 1 万条导入 | < 30s |
| 创建 Run | < 2s |
| 结果写入 | > 5000 行/s |
| 1 万条 CER 重算 | < 60s |

### 7.3 会话生命周期（四条硬规则）

1. 禁止强杀转写进程；超时发 `close` 帧并等待对端关闭。
2. 看门狗：`audio.end` 后超时无 final → 主动 close + `finalize_timeout`。
3. `engine_overloaded` 且无活跃会话 → 设备标记「需重启」，平台不自动重启。
4. 单设备实时会话上限 = `observed.realtime_slots`（网关 3）。

### 7.4 安全

- 设备凭据加密存储，报告/日志永不导出
- 只读挂载白名单，禁止任意路径读取
- 报告中的音频默认不嵌入，仅引用
- LDAP 组 → 角色映射，登录审计

### 7.5 可观测性

- 结构化日志（request_id / run_id / deployment_id）
- Run 级进度与 ETA
- 设备健康巡检（5 分钟）
- 引擎异常（overload / finalize_timeout）单独计数

**已确认**：当前阶段使用结构化日志与健康页；Prometheus/Grafana 按后续阶段处理。

### Q1 · 音频是否托管

**是什么**
数据集导入后，**原始音频文件放在哪里**。注意区分「元数据」和「音频本体」：元数据（路径、sha256、时长、参考文本）一定进 PostgreSQL；这里问的是音频字节。

**选项差异**

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A 引用 NFS | DB 只存路径 + sha256；worker 直接读挂载盘 | 导入快（只算 hash/时长，不拷贝）；不占平台空间；删数据集不影响原始素材 | 强依赖 NFS 可用与路径稳定；NFS 挂了所有评测停摆；换服务器要重新挂载 |
| B 托管 MinIO | 导入时把音频复制进对象存储，DB 存 object key | 平台自包含、可迁移、可做生命周期与权限；不受原始目录变动影响 | 导入慢一倍（要拷贝）；占空间（本机素材可能 100GB+）；开源数据集"再分发"需确认许可（内部使用一般 OK） |
| C 混合 | 小文件/热数据托管，大文件引用 | 平衡 | 实现与运维复杂度最高，先不选 |

**影响的功能**
- 导入耗时：A 约 20s/万条，B 受磁盘带宽限制，100GB 可能几十分钟
- 数据迁移：A 换机器要同步路径，B 跟着 MinIO 走
- 删除语义：A 删版本只删元数据，B 要决定是否删对象（可能被其他版本引用）
- 转码缓存：无论 A/B，`16k mono` 派生文件都建议托管

**建议：A（引用 NFS）+ 派生文件托管**
理由：原始音频只读、体量大、已有稳定挂载；派生文件小且高频读，值得托管。另需补一个「按 sha256 重新定位」功能，防止原始目录搬家后失效。

### Q2 · 说话人命名一期是否做

**是什么**
两个不同的能力：
- **分离（DER）**：回答"这段音频里有几个人、谁在什么时候说话"，输出 `说话人0/1/2` 这类**匿名编号**
- **命名（Naming）**：回答"说话人0 就是张三"，把匿名编号映射到**真实身份**

产品接口已支持：传注册声纹 → 返回 `matched_id`（就是传进去的 id）+ `confidence`。所以命名是"平台侧只需比对与统计"。

**选项差异**

| 方案 | 一期工作量 | 报告多出什么 | 风险 |
|---|---|---|---|
| A 完整命名 | +1~1.5 周 | 命名准确率、错认率、拒识率、阈值-EER 曲线、SA-DER | 需要「说话人库 + 注册音频管理」这一整套 |
| B 只做 DER | 基线 | 只有分离质量，没有身份 | 无法回答"叫没叫对" |
| C 二期 | 0 | 无 | 一期能力不完整 |

**影响的功能**
选 A 需要新增：
1. 说话人库（姓名、注册音频片段）
2. 注册音频质量校验（时长、信噪比、是否单人）
3. **按 deployment 物化声纹向量**（不同设备声纹模型不同，向量不能跨设备复用）
4. 网关容器暂存（`exec-cat` 推音频）
5. SA-DER（分离+命名联合指标）与阈值扫描

**建议：A（做）**
理由：协议已实测闭环（`matched_id` 回显、confidence 0.55~0.70），这是产品差异化能力；且不做的话，AliMeeting 这种最有价值的数据集只能用一半。

### Q3 · ITN 一期是否做

**是什么**
ITN（Inverse Text Normalization，逆文本正则化）指把口语形式转成书面形式：
- 参考/期望：`2024年3月5日`、`百分之三十`、`3.5万元`
- 模型可能输出：`二零二四年三月五日`、`百分之三十`、`三万五千元`

"ITN 准确率"就是衡量这些**数字、日期、金额、单位、百分比**有没有转对。它和 CER 不同：CER 会把"二零二四"vs"2024"算成大量字符错误，掩盖真实问题。

**选项差异**

| 方案 | 需要什么 | 能回答什么 | 成本 |
|---|---|---|---|
| A 正式 ITN 指标 | 参考侧必须有「ITN 期望文本」（人工校对或数据集自带） | ITN 准确率、过度转换率 | 高：AliMeeting 没有；方言集大多也没有 |
| B 二期 | — | — | 0 |
| C 低成本替代：数字实体分桶 | 无需额外标注，从 CER 对齐里抽"数字/单位"片段单独统计 | "数字类错误占比" | 低 |

**影响的功能**
- 选 A 需要一条**人工校对流水线**（或采购带 ITN 标注的数据集），这属于数据工程，不是平台功能
- 选 C 只需在打分时多一个切片逻辑，报告里多一个桶

**已确认：A 一期实现正式 ITN 指标，并保留数字相关 CER 近似信号。**
有 `itn_expected` 金标时按实体类型计算准确率；没有金标时正式 ITN 仍为 `N/A`，数字近似读数从与 CER 相同的编辑对齐中归因，数词写法差异也会计入错误，因此不能解释为语义 ITN 准确率。

### Q4 · 分桶规则怎么表达

**是什么**
「分桶」= 把测试集按某个维度切成子集，分子集算指标。例如：

```
整体 CER 6.8%
  ├─ 方言桶：普通话 4.2% / 粤语 9.1% / 四川话 7.8%
  ├─ 时长桶：<5s 5.1% / 5~60s 7.0% / >5min 12.4%
  └─ 场景桶：近场 3.9% / 远场 11.2%
```

**为什么必须要有**：整体指标会掩盖局部退化。典型场景是"整体没变，但粤语退化了 5pp"，没有分桶就发现不了。

**选项差异**

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A 固定维度 | 代码里写死 `dialect / duration / scene / gender / overlap`，导入时给每个 item 打 `buckets jsonb` | 简单、可索引（GIN）、UI 好做、性能稳 | 新增维度要改代码 + 重导数据 |
| B 配置 DSL | Benchmark 里写 `{name:"短句", when:"duration_ms<5000"}`，运行时解析 | 用户可自定义、无需改代码 | 要解析/校验/防注入；SQL 生成复杂；性能不可控 |
| C 预计算列 | 导入时把每种可能的桶算成列 | 查询最快 | 维度组合爆炸，表越来越宽 |

**影响的功能**
- 横评矩阵的行/列、回归对比的下钻、Badcase 的筛选，全部依赖分桶
- 选 B 会显著增加 M5/M6 的复杂度和性能风险

**已确认：A 固定维度 + 预留扩展**
固定维度落在 `item.buckets jsonb`（GIN 索引），UI 从桶的字典自动生成筛选器；二期若要自定义，再加 DSL 层，不影响已存数据。

### Q5 · 显著性计算（bootstrap 详解）

#### 问题是什么

两个系统在同一批测试集上测得 CER 6.82% 与 7.24%，差 0.42pp。这个差是**系统真的更好**，还是**这批题刚好对它有利**？

测试集是从"真实使用分布"里抽出的一个样本。换一批同等规模的题，数字会变。**bootstrap 就是估计"这个数字会怎么变"的方法。**

#### bootstrap 怎么做（四步）

```
① 把测试集看成一个整体：N 条样本，每条有 (参考字数 L_i, 错误字数 E_i)
② 有放回地抽 N 条 → 得到一份"假想的测试集"
③ 在这份假想集上重算 CER = ΣE / ΣL
④ 重复 1000 次 → 得到 1000 个 CER 值 → 它们的 2.5%~97.5% 分位就是 95% 置信区间
```

对两个系统做**配对** bootstrap：

```
每一轮都用同一组重采样下标，同时算 A 和 B 的 CER，记录 Δ = CER_B − CER_A
1000 轮 → Δ 的分布 → 95% CI 与 p 值
```

**判定规则**

| 情况 | 结论 |
|---|---|
| Δ 的 95% CI 完全 > 0 | B 比 A 差，有统计证据 |
| Δ 的 95% CI 完全 < 0 | B 比 A 好，有统计证据 |
| CI 跨过 0 | **数据不足以判断**，不能说"变好/变坏" |

#### 为什么能区分"真实差异"和"样本波动"

因为 bootstrap 模拟的正是"换一批题"这件事。如果观测到的差异比"换题造成的抖动"还小，那它就没法归因于系统。

用真实规模的模拟（每条样本参考 ~20 字、CER ~6%、1000 次重采样）：

| 测试集条数 N | 95% CI 半宽 | 能可靠识别的差异 |
|---|---|---|
| 200 | ±0.7~0.9 pp | > 1.5 pp |
| 500 | ±0.5 pp | > 1.0 pp |
| 1,000 | ±0.37 pp | > 0.7 pp |
| 2,000 | ±0.25~0.30 pp | > 0.5 pp |
| 5,000 | ±0.17~0.18 pp | > 0.35 pp |

**这就是"最小可检测差异"**：样本量不够时，0.3pp 的差异在统计上和 0 没有区别。反过来，如果只想证明"没退化"，也需要足够样本量才能给出有意义的结论。

#### 三个容易做错的细节

1. **必须配对**
   同一批题、同一组重采样下标，同时算 A 和 B。这样"题目难度"被抵消，CI 更窄。若两系统各自独立重采样，CI 约宽 1.4 倍（√2），会漏掉真实差异。

2. **重采样单元要选对**
   - CER / 标点：以 **utterance** 为单位（字符之间强相关，按字符重采样会严重低估方差）
   - DER / 命名：以 **session** 为单位（同一会话内句子高度相关）
   - 后果：AliMeeting 只有 20 个 session，**DER 的 CI 会非常宽**，只有大差异才显著。这一点必须在报告里明说，不能假装精确。

3. **多重比较**
   20 个分桶 × 5 个指标 = 100 次比较，按 5% 显著性会有约 5 个假阳性。处理：分桶对比用 BH/Holm 校正，或标注"探索性结论，未校正"。

#### 放在哪算（Q5 的三个选项）

| 选项 | 做法 | 问题 |
|---|---|---|
| A 打分时 | Run 结束算好存库 | 单 Run 的 CI 可以，但**两两对比是 N² 组合**，不可能全预算 |
| B 报告时 | 用户点对比时现算 | 灵活，但 1 万条 × 1000 次，首次打开慢 |
| **C 折中** | 单 Run 的 CI 打分时算；两两对比的 p 值报告时算 + 缓存 | 兼顾 |

**建议 C**：
- `metric_value.ci_low/ci_high` 在打分阶段写库（每个 Run 自己就有 CI）
- 对比页请求时算 Δ 的 CI 与 p，缓存键 `(run_a, run_b, metric, bucket, n_resample)`，有新 Run 时失效
- 报告统一展示：`Δ + 95% CI + p`，CI 跨 0 时显示"无显著差异"

**成本**：10,000 条 × 1,000 次重采样，用向量化实现 < 1 秒；即使纯 Python 也在数秒级，可接受。

#### 对本项目的具体含义

- AliMeeting 20 段：DER 只能识别**大于约 5pp** 的差异（以 session 为单位）；报告必须标注"样本量小，结论仅供参考"
- AISHELL-1 7,176 条：CER 可识别约 **0.3pp** 的差异
- 分桶后条数骤减（如"粤语"只有 300 条）→ CI 迅速变宽，必须显示每桶的 n

### Q6 · 后台任务用什么框架

**是什么**
导入、推理、打分、导出都是后台任务。需要：任务队列、重试、心跳、断点续跑、延迟任务。

**选项差异**

| 方案 | 生态 | 与 asyncio 契合 | 运维 | 适合场景 |
|---|---|---|---|---|
| A `arq` | 小 | 原生 async | 需 Redis | 中小规模、愿意多一个服务 |
| B Celery | 大 | 同步模型，混 async 别扭 | 需 broker + result backend | 大规模、复杂路由 |
| C **PostgreSQL 队列** | 无 | 直接 async/同步均可 | **零新增服务** | 单机、万级任务、队列与业务同库 |
| D 自研 Redis Stream | 无 | 可控 | 需 Redis + 自己维护重试 | 想深度控制 |

**影响的功能**
- 我们的调度不是普通队列：需要**设备租约**、长任务心跳、按 shard 游标拉取、熔断
- 这些语义无论用哪个框架都要自己写，框架只提供"投递/重试"

**结论：C（PG 队列）**
理由：任务量万级、单机部署、3~5 人；`job` 表 + `FOR UPDATE SKIP LOCKED` 已覆盖"领取/重试/延时/可见性超时"。
去掉 Redis 后：本机只需 `db + app` 两个容器，备份与排障都少一层。
代价：队列吞吐上限低于 Redis（本项目用不到）；`NOTIFY` 只做事件信号，不做持久化回放。

> 若将来日任务量 > 百万级，可加 Redis 作为队列后端；调度状态机不变，只换投递实现。

### Q7 · 设备凭据怎么存

**是什么**
SSH 密码/私钥、云 API Key。要能被平台解密用于连接设备，但绝不能出现在报告、导出、日志里。

**选项差异**

| 方案 | 安全性 | 运维 | 风险 |
|---|---|---|---|
| A 本地 Fernet | 中：密钥文件在服务器（600 权限） | 零依赖 | 密钥泄露=全部设备失守；备份漏了密钥就解不开 |
| B 外部 Secret（Vault/K8s Secret） | 高 | 多一个组件与权限体系 | 部署复杂，单机不划算 |
| C 环境变量/明文 | 低 | 最简单 | 极易随日志/配置泄漏 |

**影响的功能**
- 设备新增/编辑、连接测试、prepare 运维动作
- 备份与迁移：必须"数据库 + 密钥文件"一起备份

**建议：A（本地 Fernet）**
理由：单机内网、用户少；旧平台已经踩过"只备份 sqlite 没备份 key"的坑，写进运维手册即可。密钥轮换放二期。

**一期实现状态（2026-11-07）**：设备凭据使用本机 Fernet 密文表和 `data/secrets/credentials_key`；凭据 API 只返回类型与是否配置。SSH 密码/私钥已供身份采集和设备运维使用，cloud API Key 已用于 HTTPS `/v1/models` 校验。备份功能仍按 P0 范围推迟。
